## 1. 문제

현 인벤토리는 **구문 14개**(13패싯 각 1개 + `request` 2개)다. 북극성 §4가 "커버리지는 패싯 개수가 아니라 **패싯 × 구문 깊이**에서 온다"고 못 박았으므로, 패싯이 닫힌 지금 남은 작업은 전부 깊이다.

깊이가 없으면 두 가지가 막힌다.

1. **P2 트레이너의 재료 부족** — Lv1~3 다이얼을 돌릴 카드가 5장뿐이라 트레이너 자체를 검증할 수 없다.
2. **커버리지 실측 불가** — "유한 구문이 실제 캡처의 몇 %를 덮는가"(북극성 §12)를 재려면 잴 대상이 있어야 한다.

### 1-A. 이번에 드러난 결손 — 시제·상·태

설계 검토 중 확인된 사실: **인벤토리에 시제·상·태 축이 없다.**

| 요소 | 현 상태 |
|---|---|
| 현재완료 | `ask-experience`("Have you ever been ~") 1개 — 체계가 아니라 우연히 박힌 프레임 |
| 과거완료·미래완료 | 없음 |
| 진행형 | 없음 |
| **수동태** | **전무.** 웹앱 `causative-result`(get/have + O + p.p.)도 RN으로 미이식 |
| 관계절 | `SlotRole`에 자리만 있고 구문 0개 |

더 근본적으로 `Construction`은 `{function, slots, curatedVerbs, patternKind}`뿐이라 **문법 자질을 담을 자리가 없다** — 완료형이든 수동이든 슬롯 라벨 안의 문자열로만 존재한다. 그래서 "현재완료를 못 쓴다"를 시스템이 집계할 방법이 없고, SRS 롤업·회로 진단도 화행 패싯 단위로만 돈다.

이는 설계 누락이다. 북극성의 2축(구문×기능, 핵심동사)과 시제·상·태는 **직교하는 제3 차원**인데 명시적으로 다뤄진 적이 없었다. 그리고 **완료 vs 과거**(한국어에 완료상 구분이 약함)와 **수동태 회피**(한국어 능동 선호)는 사역·5형식과 같은 급의 한국인 결손이다.

## 2. 목표 / 비목표

**목표**
1. 구문 14 → **48**. 패싯당 2~5개를 실사용 빈도로 가중 배분하고, 자리마다 선정 근거가 있다.
2. 시제·상·태를 **결손 타깃 구문 + 가벼운 태그**로 흡수한다 — 화행 패싯 13은 건드리지 않는다.
3. 큐레이션 예문 카드를 구문에서 **기계 파생**해, 손저작 중복과 동기화 드리프트를 제거한다.
4. 저작 누락·부실을 배치별 게이트로 잡는다.

**비목표**
- `positional` 패턴(부사·형용사 어순) — 북극성 §10에서 P2 이후로 연기됨.
- `CURATED_VERBS` 확장 — 28개 유지. "커버리지보다 숙련"이 원래 의도이고, 신규 구문은 기존 동사셋으로 덮인다.
- 과거완료·미래완료 — 말하기 빈도가 낮아 이번 48에서 제외(§7 2차 확장 후보).
- P2 트레이너 구현. 이 스펙은 트레이너가 **소비할 재료**만 만든다.

## 4. 인벤토리 배분

### 4-A. 패싯별 목표와 자리

패싯은 균일하지 않다 — 실사용 빈도로 가중한다(요청·질문·정보는 두껍게, 의례·거절은 얇게). **목표 열이 게이트 테스트의 상수**가 된다.

| 패싯 | 현재 | 신규 | **목표** | 빈도 앵커 | 결손 타깃 |
|---|---|---|---|---|---|
| 정보·상태 전달 | 1 | +4 | **5** | `It's ~` · `S be` | 가주어 `It's hard to ~` · **수동 `It was ~ed`** |
| 방법·절차 설명 | 1 | +2 | **3** | `The way to ~` | `All you have to do is ~`(분열) |
| 사건·경험 서술 | 1 | +4 | **5** | 과거시제 서술 | `used to ~` · `was ~ing when ~` · **현재완료 `I've p.p.`** |
| 의견·평가 | 1 | +3 | **4** | `I think ~` | `It seems to me that ~` · `What I like about X is ~`(분열) |
| 동의·반대 | 1 | +2 | **3** | `Not really` | `I see your point, but ~` |
| 감정·반응 | 1 | +2 | **3** | `I'm getting ~` | `make me feel ~`(사역+감정) |
| 요청·지시 | 2 | +3 | **5** | `Could you ~` | `Let me know if ~` · **`have/get + O + p.p.`** |
| 제안·의도 | 1 | +2 | **3** | `I'm going to ~` | `Why don't we ~` |
| 조언·의무·허가 | 1 | +3 | **4** | `should` · `can`(허가) | `You don't have to ~`(부정 의무 ≠ 금지) |
| 거절·완곡 | 1 | +2 | **3** | `Maybe next time` | `I'd rather not ~` |
| 질문·확인 | 1 | +3 | **4** | `What if ~` | 부가의문문 · `Could you clarify ~` |
| 인과·조건 | 1 | +3 | **4** | `because ~` | `make O V`(사역 인과) · `so (that) ~`(목적) |
| 의례·사교 | 1 | +1 | **2** | `Sorry for ~` | — (정형 표현이라 결손 타깃 없음) |
| **합계** | **14** | **+34** | **48** | | |

**빈도 앵커** = 일상에서 반드시 쓰이는 틀. **결손 타깃** = 한국어 직역으로는 산출되지 않는 틀. 각 패싯은 두 종류를 모두 가진다 — 앵커만 있으면 번역기와 다를 게 없고, 결손만 있으면 매일 쓰는 표현이 비어 트레이너가 편향된다.

### 4-B. 동사 축이 없는 구문

조동사 틀(`You should fix this`)은 head verb가 무한 개방이고, 분열문·접속 틀은 라이트버브가 동사 자리를 채우지 않는다. 둘 다 **`curatedVerbs: []`** 로 통합한다.

`[]`는 "닫힌 후보가 없다"는 뜻이며, Lv2는 뼈대(`You should`)를 주고 학습자가 동사를 인출하므로 훈련은 그대로 성립한다. 스키마에 `verbAxis: 'closed'|'open'|'none'` 3값을 도입하는 안은 **기각** — 세 번째 상태를 지금 만들 근거가 없고 검증기·치트시트·시드 전량을 다시 손대야 한다.

## 5. `grammarFacet` — 문법 차원 태그

```ts
export const GRAMMAR_FACETS = ['perfect', 'progressive', 'passive', 'modal', 'conditional'] as const
export type GrammarFacet = (typeof GRAMMAR_FACETS)[number]

export interface Construction {
  // ...
  grammarFacet: GrammarFacet[]   // 필수 배열. 빈 배열 = 무표지(단순 현재/과거)
}
```

- 화행 패싯 13과 **직교하는 제2 태그**. 패싯 스파인은 닫힌 채로 둔다.
- **필수 배열**(빈 배열 허용) — optional(`?:`)로 두면 "안 붙였다"와 "무표지다"가 구별되지 않는다.
- 검증기는 **닫힌 집합 가드만** 건다(`isGrammarFacet`). 어떤 태그를 붙일지는 사람 판정이다.

**문법 차원이 만든 신규 구문 3개**

| 구문 | 패싯 | 태그 | 근거 |
|---|---|---|---|
| `ive-pp` — "I've already sent it." | 사건·경험 | `perfect` | 현재완료가 `ask-experience` 하나뿐이었다. 완료 vs 과거는 한국어에 대응 형태가 없다 |
| `passive-be-pp` — "It was released last week." | 정보·상태 | `passive` | 수동태 전무. 능동 선호로 회피가 고착됨 |
| `have-o-pp` — "I'll have it fixed." | 요청·지시 | `passive` | 웹앱 `causative-result` 이식. 사역+결과, 직역으로는 안 나옴 |

**기존·신규 태깅:** `ask-experience`→`perfect`, `if-cond`→`conditional`, `have-to`/신규 `should`·`can`→`modal`, `was ~ing when`→`progressive`. 나머지는 빈 배열.

## 6. 카드 파생

### 6-A. 스키마 — `Construction.domain`

```ts
export interface Construction {
  // ...
  domain: string[]   // 열린 도메인 태그 ('업무' | '일상' | 'IT' …) — 카드 domainFacet의 소스
}
```

기능 패싯(닫힌 13)과 달리 도메인은 열린 태그다(북극성 §4). 필수 필드라 시드 백필이 컴파일 타임에 강제된다 — `Slot.fill` 때와 같은 방식.

### 6-B. 파생 규칙

| 카드 필드 | 소스 |
|---|---|
| `id` | `seed-${construction.id}` |
| `text` / `meaning` | `example.en` / `example.ko` |
| `constructionId` | `construction.id` |
| `headVerb` | `curatedVerbs` 중 예문 슬롯에 표면 출현하는 **첫 동사**, 없으면 `null` |
| `functionFacet` / `domainFacet` | `function` / `domain` |
| `source` · `scaffoldLevel` · FSRS | `'curated'` · `1` · `newCardDefaults()` |
| `functionFacetSecondary` · `analysis` · `thumbnailUri` | `null` |

`headVerb` 계산은 **V4가 쓰는 `slotOfVerb`를 재사용**한다. V4가 "최소 하나는 표면에 나타난다"를 보장하므로, `curatedVerbs`가 비지 않은 구문은 항상 값을 얻는다. `[]` 구문은 자동으로 `null` → **V6 계약이 구조적으로 만족**된다(위반이 표현 불가능해짐).

손저작 5장은 제거한다. 텍스트·의미·패싯이 전부 파생값과 같고, 유일한 고유 정보인 `domainFacet`은 `Construction.domain`으로 이사한다.

### 6-C. 모듈 경계

`surfaceTokens` + `slotOfVerb`를 `validateLibrary.ts`에서 빼내 **`src/services/verbMatch.ts`** 로 옮긴다. 지금은 검증기 내부 함수지만 소비자가 둘이 되고(검증기 + 카드 파생), P2 렌더·P3 recognition도 같은 매칭을 쓴다. 검증기가 매칭 유틸을 소유하면 데이터 레이어가 서비스 레이어를 거꾸로 물게 된다.

```
data/verbForms.ts  ←  services/verbMatch.ts  ←  services/validateLibrary.ts
                                             ←  data/seedCards.ts (파생)
```

## 7. 저작 절차와 게이트

**패밀리 4배치.** 배치마다 저작 → 검증기 → 커밋. 배치가 저작 품질의 리뷰 단위다.

| 배치 | 패밀리 | 신규 |
|---|---|---|
| 1 | 정보 (3패싯) | +10 |
| 2 | 태도 (3) | +7 |
| 3 | 설득·양태 (4) | +10 |
| 4 | 상호작용 (3) | +7 |

**배치마다 통과해야 하는 게이트**
- `validateLibrary` V1~V6 전량 — 청크 경계·`fill`·동사 축을 기계가 판정
- `npm run tsc` — `domain`·`grammarFacet` 필수 필드 누락 포착
- **패싯별 카운트 테스트** — 각 패싯이 목표치를 채웠는지 단언. 저작 누락이 조용히 넘어가지 않는다
- **문법 커버 테스트** — `GRAMMAR_FACETS` 5종 각각 최소 1개 구문. 문법 차원이 빈 채로 끝나는 걸 막는다
- **파생 카드 수 = 구문 수** — 파생 누락·중복 검출

**기존 테스트 파급 (배치 1 전에 처리)**
- `library.test.ts`의 `constructionsByFunction('request')`는 **정확히 `['causative-bare','want-o-to-v']`** 를 단언한다. `request`가 5개로 늘면 깨진다 → 목록 동등 비교를 "포함 + 개수" 단언으로 바꾼다. 인벤토리가 자랄 때마다 깨지는 테스트는 게이트가 아니라 마찰이다.
- `constructions.test.ts`의 "13패싯 전량 커버"는 그대로 유효하다(커버 방향만 보므로).

**예문 유일성:** 파생 카드의 `text`가 곧 `example.en`이므로, 48개 예문은 서로 달라야 한다. 별도 규칙은 불필요 — `validateLibrary`의 기존 카드 텍스트 dedup이 정규화 기준으로 잡아준다.

**최종 상태:** 구문 48 · 파생 카드 48 · 동사셋 28(무변경) · 테스트 76 → 약 90.

## 8. 열린 위험

- **커버리지 실측은 여전히 미지수.** 48개가 실제 캡처의 몇 %를 덮는지는 P1 캡처 데이터가 있어야 안다(북극성 §12). 이번 확장은 그 실측을 **가능하게 하는 최소 자산**이지 답이 아니다. 2차 확장의 근거는 로그에서 나온다.
- **예문의 자연스러움은 기계가 못 본다.** V1~V6는 구조만 본다. "이게 진짜 원어민이 쓰는 문장인가"는 사람 판정이며 배치 커밋이 그 리뷰 지점이다. 부자연스러운 예문은 학습자에게 그대로 전이된다.
- **`grammarFacet` 5-집합의 적정성.** 관계절·비교급·부정사/동명사는 제외했다. 닫힌 집합이라 확장은 한 줄이지만, 태그가 늘면 롤업 UI(P2)의 복잡도가 함께 는다.
- **패싯당 3~4가 균일 가정.** 실사용에서 `request`·`clarify`가 `socialize`보다 훨씬 많이 쓰인다면 배분이 틀린 것이다 — 로그로 교정한다.
- **2차 확장 후보(기록):** 과거완료·미래완료, 관계절, 비교·최상급, 간접의문문.
