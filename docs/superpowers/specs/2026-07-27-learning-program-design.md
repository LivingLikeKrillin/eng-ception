# engception 학습 프로그램 — 북극성 설계 (재배치 + 인출)

> **문서 성격:** 이것은 빌드용 단일 스펙이 **아니라** 프로그램 전체의 **북극성(north-star) 설계**다. 학습 명제·메타데이터 척추·훈련 논리·로드맵을 확정하고, 그 아래로 각 Phase(P0~P4)가 **자기 스펙·플랜을 따로** 받는다. "여러 서브시스템을 한 플랜에 담지 말라"는 원칙은 여기서 **의도적으로 상위 설계만** 담고 하위를 분해함으로써 지킨다. (§7·§11 참조.)
>
> 관련: 캡처 앱 설계 `2026-07-27-capture-app-design.md`(표면·유입 계층, 이 문서가 상위 맥락으로 흡수), 웹앱 5형식 엔진 `CLAUDE.md`(레거시/이식 원천).

## 1. 문제 / 목표

### 명제 — 두 근육
engception이 기르려는 능력은 두 가지다.

1. **재배치(조합) 역량** — 머릿속 한국어를 영어로 옮기기 쉬운 구조로 재배치하고, 5형식(SVOC)으로 **우아하게** 표현하는 능력.
2. **인출(retrieval) 역량** — 백지 상태에서 재료(구문·동사·단어)를 **스스로 꺼내는** 능력.

### 재배치만으로는 안 되는 이유 (인출이 왜 1급인가)
기존 엔진(웹앱)은 영어 재료(단어·청크)를 **미리 주고 재배치만** 훈련시킨다. 이는 단어 자체를 인출하는 능력을 약화시킨다. **실제로 영어로 말해야 할 때는 백지 상태다.** 재료가 눈앞에 있는 훈련은 이 백지 상황을 준비시키지 못한다. 그래서 인출을 별도 1급 축으로 세운다.

### 제품 컨셉 — "시도의 장"
사용자가 **한국어로는 술술 나오는 익숙한 도메인**(좋아하는 소설, LoL 실시간 중계, 업무 미팅)을 **영어로 되짚어 보게** 만드는 훈련장. 도메인 지식은 이미 빠삭한데 영어로만 안 나오는 상태 — 그 간극을 반복해서 메우며 "영어식 사고"를 회로화한다.

### 유한으로 무한을 덮는다
표현 방식은 무한하지만, **유한한 개수로 높은 커버리지를 내는 패턴**을 미리 준비하면 뼈대 세우는 두려움을 없앨 수 있다. 회화 고빈도 동사도 엄선한다. 사용자 캡처에는 이 패턴을 넘는 것도 등장하지만, **패턴을 준비해야 한다는 당위는 변치 않는다.**

## 2. 핵심 설계 원리

### 원리 A — 인출과 재배치는 별개가 아니라 "비계(scaffold) 다이얼" 하나다
재배치의 고질병(재료를 미리 줌)은 사실 *비계를 안 뺀 상태*일 뿐이다. **같은 엔진에서 비계를 단계적으로 제거(fading)**하면 재배치→인출이 하나의 난이도 축으로 통합된다. 두 개의 앱이 아니다. (훈련 루프 §5.)

### 원리 B — "패턴"은 두 축의 교차다 (have/get/make 혼란의 해소)
사용자가 헷갈리던 "문법 패턴 vs 동사 다의성"은 **경쟁 분류가 아니라 서로 다른 두 축**이다.
- **축 A = 구문(Construction):** 기능→틀. "Have you ever p.p.?"(경험 묻기), "make O C"(사역). 슬롯 있는 뼈대. → *재배치·인출의 비계*.
- **축 B = 핵심 동사(Light verb):** have/get/make/take… 한 동사가 다의로 수많은 틀을 채움. → *인출 엔진*. 15~20개만 깊이 익히면 백지 커버리지가 폭발.

have/get/make의 다의성은 **동사를 고정하고 구문을 변주한 단면**이고, 5형식표는 **구문을 고정하고 동사를 변주한 단면**이다. 두 축은 교차한다. **웹앱이 이미 이 2축을 가지고 있다**(`Pattern5HId` × `CURATED_VERBS`, `causative-bare` × {make, have, let}) — 재발명이 아니라 5형식 밖으로 **일반 원리로 승격**만 하면 된다.

### 원리 C — 청킹은 산출에서 더 핵심이다
백지 문제 = **작업기억 과부하**다. 단어 단위로 지으면 문장이 끝나기 전에 WM이 터진다. 미리 뭉친 청크("have you ever", "make + O + 형용사", "meet the deadline")를 통째 인출하면 WM이 내용에 집중한다. 웹앱이 이미 이걸 한다(`[I][made him][angry]` — 단어 아닌 슬롯 청크). → **패턴을 인출 단위로, 청크를 조립 단위로.** 구문 슬롯 경계 = 청크 경계.

### 원리 D — 어순·위치 패턴은 동사 틀과 다른 부류다
부사 연쇄(장소+빈도, 장소+시점)처럼 구분자 없이 붙는 어순은 화행이 아니라 **위치·어순 패턴**이다. 패턴 라이브러리는 동사 구문뿐 아니라 어순 규칙(부사 배열, 형용사 어순)도 담는다. → `patternKind: 'construction' | 'positional'`로 분리. (positional은 v1 필수 아님, 분류 자리 확보.)

## 3. 메타데이터 backbone

사용자가 "핵심"으로 지목한 계층. **큐레이션 자료와 캡처 자료가 하나의 메타데이터 어휘를 공유**한다.

### 엔티티 ① Construction (구문 — 닫힌 큐레이션, 우리가 저작)
```ts
Construction {
  id: string                 // 'causative-bare' | 'ask-experience' ...
  function: FunctionId        // 어느 화행에 봉사하는가 (§4 패싯과 연결)
  slots: Slot[]               // 뼈대·청크 경계 (원리 C의 조립 단위)
  curatedVerbs: string[]      // 이 틀을 채우는 핵심 동사 lemma (축 B)
  patternKind: 'construction' | 'positional'   // 원리 D
  example: { en: string; ko: string }
}
```
이것이 **유한·고커버리지 백본.** 5형식 7패턴은 이 집합의 **부분집합**(승격만).

### 엔티티 ② Card (문장 인스턴스 — 큐레이션 예문 또는 사용자 캡처)
```ts
Card {
  id: string
  type: 'sentence'
  text: string                // 영어 문장 (정본)
  meaning: string | null      // 한국어 뜻 — 캡처 시 null, 지연 채움 (인출 프롬프트 전제)
  source: 'curated' | 'captured'
  constructionId: string | null   // 축 A — recognition 매핑 실패 시 null ('패턴 밖')
  headVerb: string | null          // 축 B — 핵심 동사 lemma
  functionFacet: FunctionId        // 화행 (닫힌 13, §4)
  functionFacetSecondary?: FunctionId   // 필요 시 1개까지만
  domainFacet: string[]            // 삶 — 열린 사용자 태그 (IT·물류·게임·소설…)
  scaffoldLevel: 1 | 2 | 3         // 현재 비계 단계 (§5, 숙련도 연동)
  // + FSRS 필드 (stability/difficulty/nextDueAt/lastReviewedAt/reps/lapses/cardState/lastGrade)
  createdAt: string
}
```

### 엔티티 ③ LexicalCard (어휘 인스턴스 — §6)
```ts
LexicalCard {
  id: string
  type: 'lexical'
  unit: 'word' | 'chunk'      // 낱말(라벨) | 청크(연어)
  direction: 'produce' | 'recognize'   // 기본 produce (K→E)
  text: string                // "meet the deadline" | "throughput"
  meaning: string             // 한국어 — K→E 인출 프롬프트
  collocationContext: string  // 실제 쓰임 한 줄 (낱말도 나체 아님)
  domainFacet: string[]
  sourceCardId?: string       // 어느 문장 Card에서 유래 (역추적)
  // + FSRS 필드 (Card와 동일 스케줄러 공유)
}
```

### 두 소스를 잇는 seam = recognition (웹앱 `isFiveHMoment`의 일반화)
캡처 문장을 분석할 때 *"알려진 구문을 실현하는가"*를 판정한다. 맞으면 `constructionId`/`headVerb`를 채워 그 패턴을 강화하고, 아니면 `null`로 두되 **여전히 수집·복습 가능**(패턴 밖 자산도 버리지 않음). 캡처가 큐레이션 백본을 자동으로 살찌운다.

### 확정된 기본 결정
1. **5형식 구문 = 일반 Construction 집합의 부분집합** (별도 체계 아님, 시각·코드 자산 연속).
2. **캡처 카드는 구문 태그가 없어도 됨** (`constructionId=null` 허용 — recognition이 매핑 시도, 실패해도 카드 유지).
3. **기능 패싯 = 카드당 1개(주 화행)**, 정말 필요할 때만 secondary 1개까지. (겹침 방지 vs 조합 폭발의 절충.)

## 4. 기능 패싯 (화행 spine) — 닫힌 집합 13

전이되는 능력 축이자 구문의 상위 조직자. **13개로 닫는다.** 4개 매크로 패밀리로 얕게 그룹(트리 아님).

| 패밀리 | # | 기능 패싯 | 대표 구문 씨앗 |
|---|---|---|---|
| **정보** | 1 | 정보·상태 전달 | There is~ / It's~ / S be |
| | 2 | 방법·절차 설명 | The way to~ / first…then |
| | 3 | 사건·경험 서술 | 과거시제 / Have you ever p.p. |
| **태도** | 4 | 의견·평가 | I think~ / find O C |
| | 5 | 동의·반대 | I don't think~ / Not really |
| | 6 | 감정·반응 | I'm so ~ that / make me feel |
| **설득·양태** | 7 | 요청·지시 | Could you~ / want O to V / 사역 |
| | 8 | 제안·의도 | Let's~ / I'm going to~ |
| | 9 | 조언·의무·허가·능력 | should / have to / can |
| | 10 | 거절·완곡 | I'm afraid~ / I'd rather not |
| **상호작용** | 11 | 질문·확인 | Do you mean~ / What if |
| | 12 | 인과·조건 | because~ / If~ / make O V |
| | 13 | 의례·사교 | greet / thank / apologize |

**커버리지 근거:** 미팅 비즈니스영어 = 1·4·5·7·11에 매핑; LoL 중계 = 2·3·6; 소설 = 3·4. 도메인은 열린 태그(패싯 2축), 화행은 이 13개 고정.
**세분도 원칙:** 2단계 이상 중첩 금지, 위계 대신 패싯 태그. 커버리지는 패싯 개수가 아니라 **패싯 × 구문 깊이**에서 온다 → 패싯은 13에서 닫고 깊이는 구문 인벤토리(§11-A)로.

## 5. 훈련 루프 (비계 다이얼)

목표 발화 하나(한국어 뜻 → 영어 산출)를, 카드 성숙도에 따라 비계를 걷어내며 반복한다.

| Lv | 이름 | 제공 | 산출 | 채점 |
|---|---|---|---|---|
| **1** | 재배치(조립) | 영어 청크 전부 | 순서·connector | 자동(`assemblyCorrect`) |
| **2** | 부분 인출 | 구문 뼈대만 (`Have you ever ___?`) | 내용어·동사 인출 | 혼합 |
| **3** | 완전 인출(백지) | 한국어 뜻(+화행 힌트)만 | 영어 통째 산출 → 모범답·구문 공개·대조 | 자가평가(`gradeFromSelfRating`) |

- **fading = 자동 걷어내기:** 새 카드는 Lv1, FSRS 숙련도가 오르면 Lv2→Lv3로 자동 승급. **비계 제거 = 학습 진행 = SRS 곡선.** 별도 커리큘럼 불필요.
- **두 재료 소스 모두 사용:**
  - **큐레이션 카드** — 한국어·구문이 저작돼 있어 Lv1~3 즉시 가능.
  - **캡처 카드** — 캡처 시 영어만. 복습 진입 시 Claude 1호출로 `meaning`+구문/동사 채움 → 그때부터 Lv2/Lv3 가능(지연·캐시). 뜻 없는 카드는 Lv1(읽기/shadow)까지만.

### 확정된 기본 결정
1. **비계 승급 = 숙련도 연동 자동** + "백지 도전" 수동 점프 옵션. 매 카드 모드를 사용자가 고르게 하지 않음(선택 피로 방지).
2. **캡처 카드의 Lv3 프롬프트 = 한국어 뜻** → "뜻 채우기"가 인출 훈련의 전제.

## 6. 어휘 인출 레이어 (내용어)

원리 B의 축 B(핵심 동사)를 넘어, **도메인 내용어를 백지에서 꺼내는** 능력. §1 인출 근육의 나머지 절반.

**안티패턴:** 양방향 낱말 플래시카드 사일로가 **아니다.** 세 원칙으로 차별화한다.

1. **단위 = 병목에 맞춘다.** 병목이 연어면 **청크**(`meet the deadline`, `gank mid`), 병목이 라벨 자체면 **낱말**(`throughput`, `invoice`). `unit: 'word' | 'chunk'`. 대략 명사·전문용어=낱말 경향, 동사·형용사·기능구=청크 경향. **낱말도 `collocationContext`(쓰임 한 줄)를 달아 나체가 아니게** 한다.
2. **방향 = 기본 생산적 인출(K→E).** 재인(E→K)은 read-only 전문용어용 카드별 옵션(`direction`), 기본값은 produce.
3. **소스 = organic.** 구문·핵심동사는 우리가 큐레이션(유한·전이), **내용어는 대부분 사용자 캡처에서 유래**(도메인 패싯 소유). 큐레이션 도메인 단어장은 v1에서 최소/없음(일반 단어앱 함정 회피).

**카드 탄생 경로 (엔진 통합, 사일로 아님):**
- **(a) Lv3 백지 실패 → 자동 승격.** 못 꺼낸 청크/낱말이 어휘 카드로. 실패 지점이 곧 커리큘럼.
- **(b) 캡처 카드에서 탭-저장.** 문장 속 청크/낱말을 탭해 어휘 카드로(`sourceCardId` 기록).
- **(c) 큐레이션 시드 = 연기.** 필요 확인 시 후속.

**통합:** 어휘 카드는 **문장 카드와 같은 FSRS·같은 컬렉션·같은 인출 UI**를 쓰되 별도 큐. 어휘 인출이 문장 산출로 되먹임(문장 Lv3에서 뽑히고, 어휘가 서면 문장이 쉬워짐). 그래서 "별도 앱"처럼 느껴지지 않는다.

## 7. 표면 전략 & 로드맵

### 표면 = RN 앱으로 수렴 (확정)
- **RN 앱(engception-capture) = 제품 본체.** 아래 4레이어 전부 여기 안착. 캡처·인출 훈련 루프가 **한 폰에서 닫힌다**(캡처→훈련이 두 앱으로 쪼개지지 않음).
- **웹앱 = 레거시/레퍼런스.** 5형식 엔진의 순수 TS 로직(prompts·patternLabels·조립 판정·srs)은 **RN 트레이너로 이식**. 웹 자체는 더 키우지 않음.
- **5형식이 "나중 합류"에서 "Lv1의 코어"로 앞당겨짐** — 기존 캡처 앱 설계의 "5형식 나중 합류" 스코프를 이 문서가 확장한다.

### 4개 레이어 (표면이 아니라 척추부터)
```
L1  메타데이터 backbone   — Construction/Card/LexicalCard 스키마 + 13 기능패싯   [공유 척추]
L2  패턴 라이브러리 콘텐츠  — 딜리버러블 A(구문 인벤토리)·B(핵심동사)·큐레이션 카드·시드 어휘
L3  훈련 엔진             — 비계 다이얼 Lv1~3 + FSRS + recognition seam + 어휘 승급
L4  표면(surface)        — 캡처 유입 · 트레이너 UI · 컬렉션(패싯 필터)
```
**핵심 진단:** 그동안 L4(캡처=표면)만 파고 L1·L2(척추)가 비어 있었다. L1·L2는 **기기 불필요·저작 작업** — 폰 세팅을 기다리는 동안 지금 착수 가능.

### 로드맵 (기존 캡처 M1을 버리지 않음)
| Phase | 내용 | 기기 | 상태 |
|---|---|---|---|
| **P0** | L1 스키마 + L2 시드(13패싯 × 구문 몇 개 + 동사셋 + 큐레이션 카드 N + 시드 어휘) | ❌ 불필요 | **다음 착수** |
| **P1** | 캡처 M1 마무리 (유입·수집) + 어휘 탭-저장(b) | ✅ 필요 | Chunk 1-2 완료, 3-4 대기 |
| **P2** | 트레이너 Lv1~3(비계 다이얼) + 어휘 Lv3 승급(a) — L2·캡처카드 소비 | 표면 | 신규 |
| **P3** | Claude 분석 = recognition(캡처→구문 매핑) + 지연 번역/성분분석 = 캡처 M2 | — | 신규 |
| **P4** | 클라우드 동기화(구글 로그인 + Firestore + 비파괴 병합) = 캡처 M3 | — | 신규 |

각 Phase는 이 북극성 아래에서 **자기 스펙·플랜을 따로** 받는다. P0가 즉시 착수 지점.

## 8. 재료 소스의 대칭 (설계 미학)
- **프레임(구문·핵심동사·기능패싯) = 우리가 큐레이션.** 유한·전이·닫힘.
- **내용(도메인 문장·내용어) = 사용자가 캡처.** 무한·개인·열림.
- recognition seam이 둘을 잇는다. "우리 자료가 뼈대, 사용자 삶이 살." 이 대칭이 캡처 기능의 존재 이유를 학습 명제와 정렬시킨다.

## 9. 재사용 vs 신규 (프로그램 차원)
| 물려받음 (순수 TS 로직) | 재작성/신규 |
|---|---|
| `srs.ts` (FSRS, 이미 이식됨) | 트레이너 UI Lv1~3 + 비계 승급 로직 |
| `srsView.ts` (isDue/masteryLabel) | 어휘 레이어(LexicalCard + K→E 인출 UI) |
| 5형식 조립 판정·prompts·patternLabels (이식) | Construction/Card/LexicalCard 스키마 + 라이브러리 |
| `DataStore` 인터페이스 + `db` 파사드 | recognition seam(캡처→구문 매핑) |
| `validate.ts` / `claude.ts` 패턴 | 기능 패싯 13 + 구문 인벤토리(콘텐츠) |
| 캡처 유입(카메라·OCR, 캡처 앱 M1) | 컬렉션 패싯 필터 UI |

## 10. 범위 밖 (Deferred)
- **구문 인벤토리·핵심동사셋 전체 저작** — P0의 딜리버러블(§11), 이 북극성 문서에서 전량 열거하지 않음.
- **positional 패턴(부사·형용사 어순 미니드릴)** — 분류 자리만 확보, 구현은 후속.
- **큐레이션 도메인 단어장(어휘 시드 c)** — organic 소스로 부족 확인 시.
- **어휘 recognize 방향의 본격 UX** — 옵션만 스키마에 열어둠.
- **역방향 산출(A)·구조 드릴(B) 등 추가 복습 모드** — Lv 다이얼 이후.
- **iOS / 오디오·TTS(engception-listen) / 카카오 로그인** — 기존 캡처 앱 설계의 deferred 승계.

## 11. 후속 딜리버러블 & 다음 단계
- **이 문서 = 북극성.** 명제 + 메타데이터 척추 + 훈련 논리 + 로드맵 확정.
- **딜리버러블 A (구문 인벤토리):** 13 기능패싯별 고커버리지 Construction 목록 저작. P0 스펙에서 상세화.
- **딜리버러블 B (핵심 동사셋):** 웹앱 17개(5형식 전용)를 일상 회화 고빈도 동사(be/do/go/take/put/keep…)로 확장. P0 스펙에서 상세화.
- **다음:** **P0(메타데이터 스키마 + 패턴 라이브러리 시드)**가 별도 스펙 → 플랜 → 구현으로 진행. 기기 불필요하므로 폰 세팅과 병행 가능.

## 12. 열린 위험 / 검증 필요
- **recognition 정확도:** 캡처 문장→구문 매핑을 Claude가 얼마나 정확히 하는가. `validate.ts`로 형식 가드, 내용 오류는 `null`(패턴 밖) 낙하로 흡수.
- **어휘 자동 승급(a)의 노이즈:** Lv3 실패가 진짜 어휘 결손인지 단순 실수인지. 승급 임계(연속 실패 N회 등) 튜닝 필요 — 데이터 게이팅.
- **비계 자동 승급 임계:** 어느 숙련도에서 Lv1→2→3로 올릴지. FSRS stability 컷 실측 후 튜닝.
- **구문 인벤토리 커버리지 실측:** 유한 구문이 실제 캡처의 몇 %를 덮는지. 초기 사용 로그로 검증 후 인벤토리 보강.
- **RN 이식 비용:** 웹 5형식 엔진(React DOM UI)의 로직/뷰 분리 정도. 순수 로직은 이식 쉬움, UI는 재작성. P2 스펙에서 경계 명시.
